## 0. 结论先行

### 0.1 一句话结论

**光影开着时，我们自己的 `ShaderInstance` 仍然被绑定并执行，但 Iris 在 `ShaderInstance.apply()` 的 TAIL 把 `glColorMask` 和 `glDepthMask` 全关了 —— 几何被光栅化了却一个像素都写不出去。** 这就是"自定义着色器根本不执行"的真正机制，不是 program 被替换。

**要让图案在光影下可见，最短路径不需要改光影包、也不需要注入 Iris：把绘制挪到 `RenderLevelStageEvent.Stage.AFTER_LEVEL`（Iris 的 final pass 之后）即可，此时写入锁已随 `isRenderingWorld=false` 解除。**

**要让图案"参与光影的光照/泛化/合成"，没有官方接口。** 只能靠内部注入（mixin/反射改 Iris 的 `ProgramSource` / pass 表）或直接改光影包。

### 0.2 路线判定表

| # | 路线 | 图案可见 | 参与光影光照/泛化 | 几何遮挡 | 改动面 | 分发 | 结论 |
|---|------|----------|------------------|----------|--------|------|------|
| A | 现状：世界渲染阶段用自建 RenderType + ShaderInstance（AFTER_ENTITIES 等） | ❌ 完全不可见 | — | — | 0 | — | **不可行**（写掩码锁，见 §5） |

### 0.3 给本项目的建议

1. **马上能做**：把星刃绘制时机切到 `AFTER_LEVEL`，图案立刻在光影下可见、且可被几何遮挡。这一步不依赖任何 Iris 内部结构，风险最低。
2. **想要"真·光影效果"**（被泛光、被 TAA/FXAA 处理、跟随色调映射）：**自己用**时改光影包最划算（加 `composite3` 或 `composite8`）；**要随 mod 分发**时只能走 §8 的内部注入，并接受"每个 Iris 版本可能失效"的代价。
3. 若接受"只叠最终画面之上"，路线 B 已经够用，且不需要碰 Oculus 一行代码。

## 1. 光影包管线实况（问题 1）

### 1.1 目录结构

解包后 `shaders/` 下是"三套维度外壳 + 一套共享实现"：

```
shaders/
├─ shaders.properties          # 包配置（含 Custom Uniforms 段）
├─ block.properties / entity.properties / item.properties
├─ lang/
├─ lib/                        # 噪声、云等纹理
├─ program/                    # 25 个 .glsl，真正被 include 的实现
│    gbuffers_*.glsl (16 个) / deferred1.glsl / composite.glsl / composite2.glsl
│    composite4.glsl / composite5.glsl / composite6.glsl / composite7.glsl
│    final.glsl / shadow.glsl / template.glsl
├─ world0/    # 主世界外壳：每个 pass 一对 .fsh/.vsh，内容只有
│             #   #version 130 / #define OVERWORLD / #include "/program/xxx.glsl"
├─ world1/    # 末地
└─ world-1/   # 下界
```

`world0/` 下实际存在的 pass 文件（`Get-ChildItem shaders\world0`）：

- `gbuffers_armor_glint`, `gbuffers_basic`, `gbuffers_beaconbeam`, `gbuffers_block`, `gbuffers_clouds`, `gbuffers_damagedblock`, `gbuffers_entities`, `gbuffers_entities_glowing`, `gbuffers_hand`, `gbuffers_line`, `gbuffers_skybasic`, `gbuffers_skytextured`, `gbuffers_spidereyes`, `gbuffers_terrain`, `gbuffers_textured`, `gbuffers_water`, `gbuffers_weather`
- `deferred1`
- `composite`, `composite2`, `composite4`, `composite5`, `composite6`, `composite7`
- `final`
- `shadow`

**注意：没有 `composite1`、没有 `composite3`** —— Iris 允许编号不连续。证据：`net.irisshaders.iris.shaderpack.programs.ProgramSet#readProgramArray` 开头 `bipush 100`（上限 100 个），按编号逐个尝试读取，存在才收集，最终数组按编号升序排列（`ProgramSet` 字段 `ProgramSource[] composite`、`ProgramSource[] deferred`）。

### 1.2 执行顺序

Iris 的 pass 顺序由 `net.irisshaders.iris.shaderpack.loading.ProgramGroup` 枚举定义，顺序为：

```
Setup, Begin, Shadow, ShadowComposite, Prepare, Gbuffers, Deferred, Composite, Final, Dh
```

（`javap` 输出该枚举的常量声明顺序即此顺序。）对应到本包：

```
shadow
  → gbuffers_*（地形/实体/天空/云/天气/水/手…）
  → deferred1
  → composite → composite2 → composite4 → composite5 → composite6 → composite7
  → final
```

`shaders.properties` 里的 `program.<dim>/<pass>.enabled=<条件>` 只控制**开关**，不改变顺序：

```
program.world0/composite2.enabled=MOTION_BLURRING
program.world0/composite4.enabled=BLOOM
program.world0/composite6.enabled=TAA
program.world0/composite7.enabled=FXAA
（world-1 / world1 同样四行）
shadow.enabled=REALTIME_SHADOWS
```

### 1.3 每个 pass 读写哪些缓冲（决定图案该插在哪）

从各 program 的 `DRAWBUFFERS` 注释与 `texelFetch` 读取点（行号为 `shaders/program/xxx.glsl` 内行号）：

| pass | 读 | 写（DRAWBUFFERS） | 文件:行 |
|------|----|------------------|---------|
| `gbuffers_basic` | — | `0`（colortex0） | `gbuffers_basic.glsl:113` |
| `gbuffers_entities` | — | `01`，带法线分支 `015` | `gbuffers_entities.glsl:174,179` |
| `gbuffers_textured` | gaux1 | `013` | `gbuffers_textured.glsl:167` |
| `deferred1` | colortex0/1/3/5/7 + `depthtex0` | `054`（+`7`） | `deferred1.glsl:38-67,225,415,420` |
| `composite` | colortex0 + `depthtex0`/`depthtex1` | `0`（+`4`） | `composite.glsl:25,49,98-100,162,166` |
| `composite2` | — | `0` | `composite2.glsl:115` |
| `composite4`（BLOOM） | colortex3 等 | `3` | `composite4.glsl:75` |
| `composite5` | — | `3` | `composite5.glsl:210` |
| `composite6`（TAA） | — | `3` | `composite6.glsl:53,57` |
| `composite7`（FXAA） | `colortex3` | `3` | `composite7.glsl:40` |
| `final` | `colortex3` | `0` → 屏幕 | `final.glsl:66` |

结论：**colortex3 是后处理链的"最终图像"缓冲**（bloom→TAA→FXAA 都写它），`final` 只读 colortex3 就写屏。

### 1.4 最后一步写回主帧缓冲的是谁

- 文件：`shaders/world0/final.fsh`（`#version 130` + `#include "/program/final.glsl"`）
- 实现：`shaders/program/final.glsl` 末尾
  ```glsl
  vec3 color = texture2D(colortex3, texCoordM).rgb;
  ... IMAGE_SHARPENING ...
  /* DRAWBUFFERS:0 */
  gl_FragData[0] = vec4(color, 1.0);
  ```
- 它写到的 FBO 不是"某个 Iris 自己的 gbuffer"，而是**直接挂 Minecraft 主 RenderTarget 的颜色纹理**：

`net.irisshaders.iris.pipeline.FinalPassRenderer#renderFinalPass()`（字节码）：

```java
RenderSystem.disableBlend();
RenderSystem.depthMask(false);
RenderTarget main = Minecraft.m_91087_().m_91385_();     // getMainRenderTarget()
int w = main.f_83915_, h = main.f_83916_;
int colorTex = main.m_83975_();                          // getColorTextureId()
colorHolder.addColorAttachment(0, colorTex);
colorHolder.bind();
FullScreenQuadRenderer.INSTANCE.begin();
... 用 finalPass.program 全屏 quad ...
```

并且 `FinalPassRenderer` 构造时 `colorHolder = new GlFramebuffer()`，**只 addColorAttachment(0, 主颜色纹理)，没有任何 `addDepthAttachment`** —— 所以 final pass 的输出 FBO 没有深度附件。

## 2. Iris/Oculus 的接管点（问题 2）

### 2.1 最终 pass 在 `renderLevel` 的哪个位置

`net.irisshaders.iris.mixin.MixinLevelRenderer` 里（`javap -v` 的 `RuntimeInvisibleAnnotations`）：

```java
@Inject(method = "renderLevel", at = @At(value = "RETURN", shift = At.Shift.BEFORE))
private void iris$endLevelRender(...) {
    Minecraft.getInstance().getProfiler().push("iris_finalize");
    Iris.getPipelineManager().getPipeline().ifPresent(WorldRenderingPipeline::finalizeLevelRendering);
    ...
}
```

即：**`LevelRenderer.renderLevel` 方法体最后一条语句之前**，Iris 跑完合成并写屏。

`net.irisshaders.iris.pipeline.IrisRenderingPipeline#finalizeLevelRendering()` 字节码极短，只有三步：

```java
public void finalizeLevelRendering() {
    this.isRenderingWorld = false;          // ← 关键：立刻解除"接管世界渲染"状态
    this.compositeRenderer.renderAll();     // composite 全链
    this.finalPassRenderer.renderFinalPass(); // final → 主颜色纹理
}
```

注意：**没有把深度拷回主帧缓冲的步骤**。

### 2.2 `renderLevel` 内的其它 Iris 钩子（同一 mixin）

`MixinLevelRenderer` 还注入：`iris$setupPipeline`（`renderLevel` HEAD）、`iris$beginLevelRender`（INVOKE + AFTER）、`iris$beginSky/endSky`、`iris$beginClouds/endClouds`、`iris$beginTerrainLayer/endTerrainLayer`、`iris$beginWeather/endWeather`、`iris$beginWorldBorder/endWorldBorder`、`iris$beginTranslucents`（`@At(value="CONSTANT", args="stringValue=translucent")`，即在半透明阶段开始前、实体之后）、`iris$resetDebugRenderStage` 等。方法名常量池里可见 `finalizeLevelRendering`、`m_91087_`、`m_91307_`、`m_6182_`。

（同名 `MixinLevelRenderer` 还有多份，分别在 `net.irisshaders.iris.mixin.shadows`、`net.irisshaders.iris.mixin.sky`（`MixinLevelRenderer_SunMoonToggle`）、`net.irisshaders.iris.mixin.vertices.immediate`、`net.irisshaders.iris.mixin.batchedentityrendering`（`MixinLevelRenderer_EntityListSorting`）——文中的结论只针对 `net.irisshaders.iris.mixin.MixinLevelRenderer`。）

### 2.3 Iris 到底"替换"了什么

不是"所有 RenderType 的 program"。证据：

- `net.irisshaders.iris.mixin.MixinGameRenderer` 有几十个 `getRendertype*Shader` 的 `@Inject(HEAD, cancellable)`：`getRendertypeSolidShader`、`getRendertypeCutoutShader`、`getRendertypeTranslucentShader`、`getRendertypeEntityCutoutShader`、`getRendertypeEntityTranslucentShader`、`getRendertypeGlintShader`、`getRendertypeTextShader`、`getRendertypeLinesShader`、`getRendertypeWaterMaskShader`、`getRendertypeBeaconBeamShader`、`getRendertypeEntityEyesShader`、`getRendertypeLeashShader`、`getRendertypeLightningShader`、`getRendertypeCrumblingShader`、`getRendertypeTextBackgroundShader` 等 —— **替换的是原版"取 shader"的入口**。
- `net.irisshaders.iris.mixin.MixinProgramManager` 只有一个 `iris$releaseGeometry`（释放 geometry/tess 程序），**没有拦截 `ProgramManager.getOrCreate`**。
- `net.irisshaders.iris.mixin.MixinProgramType` 只是往 `Program$Type` 枚举里加 GEOMETRY/TESS_CONTROL/TESS_EVAL。
- 我们自己的 `RenderType` 是通过 `RenderStateShard.ShaderStateShard(shader)` 绑定的（`StarRenderTypes.java`），Iris 没有碰这条路径。

**所以"我们的 program 被换掉了"这个判断是错的。真正的问题在下一节。**

## 3. 为什么现在完全看不见：Iris 的写掩码锁（核心发现）

### 3.1 机制

`net.irisshaders.iris.mixin.MixinShaderInstance`：

```java
@Inject(method = "apply", at = @At("TAIL"))
private void iris$lockDepthColorState(CallbackInfo ci) {
    if (this instanceof ExtendedShader || this instanceof FallbackShader) return; // Iris 自己的程序放行
    if (shouldOverrideShaders()) DepthColorStorage.disableDepthColor();
}

@Inject(method = "clear", at = @At("HEAD"))
private void iris$unlockDepthColorState(CallbackInfo ci) {
    DepthColorStorage.unlockDepthColor();
}
```

`shouldOverrideShaders()`：

```java
Iris.getPipelineManager().getPipelineNullable() instanceof ShaderRenderingPipeline p ? p.shouldOverrideShaders() : false
```

`net.irisshaders.iris.pipeline.IrisRenderingPipeline#shouldOverrideShaders()` 字节码：

```java
return this.isRenderingWorld && this.isMainBound;
```

- `isRenderingWorld`：`beginLevelRendering()` 置 true，`finalizeLevelRendering()` 第一句置 false。
- `isMainBound`：`beginLevelRendering()` 里对主 RenderTarget 调 `m_83947_(true)` 之后置 true；之后由 `net.irisshaders.iris.mixin.state_tracking.MixinRenderTarget#iris$onBindFramebuffer` 在每次 `RenderTarget.bindWrite` 时更新（`bound == Minecraft.getMainRenderTarget()`）。Iris 自己的 `GlFramebuffer.bind()` 不是 `RenderTarget`，不触发这个更新，所以**整个世界渲染期间 `isMainBound` 保持 true**。

`net.irisshaders.iris.gl.blending.DepthColorStorage#disableDepthColor()` 字节码：

```java
if (!depthColorLocked) {
    ColorMask orig = GlStateManagerAccessor.getCOLOR_MASK();
    DepthState d = GlStateManagerAccessor.getDEPTH();
    originalDepthEnable = d.f_84627_;
    originalColor = new ColorMask(orig.f_84608_, orig.f_84609_, orig.f_84610_, orig.f_84611_);
}
depthColorLocked = false;
GlStateManager._depthMask(false);
GlStateManager._colorMask(false, false, false, false);   // ★ 全部颜色通道关闭
depthColorLocked = true;
```

`unlockDepthColor()` 才把 `_depthMask(originalDepthEnable)` 与 `_colorMask(...)` 恢复。

### 3.2 结论

世界渲染期间（`AFTER_ENTITIES` / `AFTER_PARTICLES` / `AFTER_WEATHER` 等）我们画星刃：

1. `ShaderStateShard` 绑定我们的 `ShaderInstance` → `apply()` 正常执行；
2. `apply()` 返回瞬间被 Iris 注入 → `glDepthMask(false)` + `glColorMask(0,0,0,0)`；
3. 顶点提交、片元着色器执行、**但没有任何颜色/深度写出去**；
4. `clear()` 时才解锁（此时这一批几何已经画完）。

**这与"程序没执行"的表现完全一致，但其实是"执行了、写不出去"。** 也解释了为什么关光影一切正常。

### 3.3 这条锁正好是 AFTER_LEVEL 的解法

`finalizeLevelRendering()` 第一句 `isRenderingWorld = false`，所以 **final pass 之后的所有绘制，`shouldOverrideShaders()` 都是 false，锁不再生效**。`AFTER_LEVEL` 事件恰好在这个时间点之后（见 §4）。

| AFTER_BLOCK_ENTITIES | 1827 / 1842 |

```
LevelRenderer.renderLevel
  ├─ … AFTER_SKY → 地形/实体 (AFTER_ENTITIES) → 方块实体 → 粒子 → 天气 …
  ├─ iris$beginTranslucents  → Iris deferred1
  ├─ 半透明/手部之前…
  └─ [RETURN 前] iris$endLevelRender → IrisRenderingPipeline.finalizeLevelRendering()
        ├─ isRenderingWorld = false
        ├─ compositeRenderer.renderAll()      （composite→…→composite7）
        └─ finalPassRenderer.renderFinalPass() → 主 RenderTarget 颜色纹理 ★写屏
return 到 GameRenderer
  ├─ Forge AFTER_LEVEL 事件   ← 在写屏之后
  └─ hand：RenderSystem.clear(DEPTH) → renderItemInHand
（之后）GameRenderer.renderLevel 的 TAIL → iris$runColorSpace（色彩空间转换）
```

证据：`MixinLevelRenderer#iris$endLevelRender`（RETURN+BEFORE）、`IrisRenderingPipeline#finalizeLevelRendering`、`MixinGameRenderer#iris$runColorSpace`（`@Inject(method="renderLevel", at=@At("TAIL"))`）、`GameRenderer#m_109089_` 上述偏移。

### 4.3 逐时机结论

| 时机 | 相对 Iris final pass | 写入锁 | 场景深度 | 能否画出来 |
|------|---------------------|--------|----------|-----------|
| `AFTER_SKY` / `AFTER_ENTITIES` / `AFTER_BLOCK_ENTITIES` / `AFTER_PARTICLES` / `AFTER_WEATHER` | **之前**（在世界渲染内） | 🔒 生效（isRenderingWorld=true） | 有（gbuffer 的 depth 附件＝主 target 的深度纹理） | ❌ 被写掩码锁吞掉 |
| `AFTER_LEVEL` | **之后** | 🔓 解除（isRenderingWorld=false） | 有（此刻仍是场景深度；手部渲染在它之后才 `clear(DEPTH)`） | ✅ **可以** |
| `RenderGuiEvent.Post` / `ScreenEvent.Render` | 之后 | 🔓 | ⚠️ 手部渲染已 `clear(DEPTH)`，深度没了 | ✅ 可以，但无遮挡 |
| 自己 mixin 到 `finalizeLevelRendering` 内部 | — | — | — | 见 §8 |

**所以：唯一"既能画出来、又能拿到场景深度、又不用碰 Iris 内部"的时机是 `RenderLevelStageEvent.Stage.AFTER_LEVEL`。**

## 5. 深度与遮挡（问题 4）

### 5.1 深度在哪

关键事实：**Iris 的 gbuffer FBO 并不拥有自己的深度纹理，而是挂载 Minecraft 主 RenderTarget 的深度纹理。**

`IrisRenderingPipeline#beginLevelRendering()` 字节码（偏移 382~441）：

```java
RenderTarget main = Minecraft.m_91087_().m_91385_();        // getMainRenderTarget()
int depthTex = main.m_83980_();                              // getDepthTextureId()
int depthFmt = DepthBufferFormat.fromGlEnumOrDefault(
        TextureInfoCache.INSTANCE.getInfo(depthTex).getInternalFormat());
renderTargets.resizeIfNeeded(
        ((Blaze3dRenderTargetExt) main).iris$getDepthBufferVersion(),
        depthTex,
        main.f_83915_, main.f_83916_,
        depthFmt, packDirectives);
...
main.m_83947_(true);         // bindWrite(true)
isMainBound = true;
```

`net.irisshaders.iris.targets.RenderTargets#resizeIfNeeded(int depthBufferVersion, int depthTexture, int width, int height, DepthBufferFormat, PackDirectives)` 内部把 `currentDepthTexture` 设为传入的 id，gbuffer framebuffer 通过 `GlFramebuffer.addDepthAttachment(int)` 挂上它（同一方法字节码里可见 `addDepthAttachment` 与 `hasDepthAttachment`）。

结论：

- 主帧缓冲的**深度附件在整个世界渲染期间就是真实场景深度**（Iris 的 gbuffer 往它里面写）；
- `final pass` 绑的是 `colorHolder`（只有颜色附件、无深度），`bind` 它并不会清掉主 target 的深度纹理内容；`final` 自己 `depthMask(false)`；
- 手部渲染之前 `GameRenderer` 会 `RenderSystem.clear(256)` 清深度 —— **`AFTER_LEVEL` 是最后一个"场景深度还在"的时机**。

### 5.2 遮挡怎么做（推荐做法）

在 `AFTER_LEVEL`：

```java
Minecraft mc = Minecraft.getInstance();
mc.getMainRenderTarget().bindWrite(true);   // 重新绑定主 target：拿到颜色 + 深度
RenderSystem.enableDepthTest();
RenderSystem.depthFunc(GL_LEQUAL);          // 515
RenderSystem.depthMask(false);              // 只测不写
// 绘制几何（用 event.getPoseStack() / event.getProjectionMatrix()，与场景同一套矩阵）
```

因为绑的是主 target 本身，深度测试直接对着真实场景深度 → **被方块/实体遮挡的部分自然被裁掉**。这一步不需要 `gl_FragDepth`、不需要 `DepthClamp`、不需要读 `depthtex0`。

如果要的是"屏幕空间软遮挡/接触阴影"，可以采样 `depthtex0`，但 **Iris 没有公开 getter 拿 `RenderTargets`**（`IrisRenderingPipeline.renderTargets` 是 private 字段，`WorldRenderingPipeline` 接口里也没有任何返回深度/RenderTargets 的方法，见 §8.1），要走反射或 mixin。而 `depthtex0` 与主 target 的深度附件是同一张纹理，把它当 sampler 采样的同时我们又往同一 FBO 的**颜色**附件写，属于"反馈回路"的灰区（只读深度、只写颜色，多数驱动接受，但规范上是 UB）；更稳的做法是先把主深度 `glCopyImageSubData` / blit 到一张自己的纹理再采样。

### 5.3 `gl_FragDepth` 能不能用

能（我们的 `ShaderInstance` 就是普通 GLSL 程序），但它只影响我们自己的几何写入的深度值，解决不了"我们根本不知道场景深度"的问题；在 `AFTER_LEVEL` 绑主 target 时，深度测试本身已经给到遮挡，`gl_FragDepth` 只在"软边/溶解"这类需求上才有意义。

## 8. 内部注入：能不能让 mod 把自己的 GLSL 交给 Iris 执行（问题 8-2/8-3/8-4/8-5）

### 8.1 结构上可行吗：可行，且切入点比想象中干净

关键类/签名（全部 `javap` 实测）：

- `net.irisshaders.iris.shaderpack.programs.ProgramSource`
  - **public 构造器**：`ProgramSource(String name, String vertex, String geometry, String tessControl, String tessEval, String fragment, ProgramSet parent, ShaderProperties props, BlendModeOverride blend)`
  - private 构造器多一个 `ProgramDirectives` 参数（保留原 pass 的 `drawBuffers`/`blend` 等指令，走反射时更该用这个）
  - `getVertexSource()/getGeometrySource()/getTessControlSource()/getTessEvalSource()/getFragmentSource()` 返回 `Optional<String>`
  - `getDirectives()`、`getParent()`、`withDirectiveOverride(ProgramDirectives)`
  - → **可以用内存里的任意 GLSL 文本构造一个 program 源**，不需要碰磁盘。
- `net.irisshaders.iris.shaderpack.programs.ProgramSet`
  - `ProgramSet(AbsolutePackPath root, Function<AbsolutePackPath,String> sourceProvider, ShaderProperties, ShaderPack)` —— 源码来自**函数**而不是文件，结构上支持"内存包"
  - `getComposite()`、`getCompositeFinal()`、`getDeferred()`、`getGbuffers*()`、`get(ProgramId)`
- `net.irisshaders.iris.pipeline.programs.ShaderCreator`
  - `public static ExtendedShader create(WorldRenderingPipeline, String name, ProgramSource, ProgramId, GlFramebuffer drawingBuffer, GlFramebuffer vertexBuffer, AlphaTest, VertexFormat, ShaderAttributeInputs, FrameUpdateNotifier, IrisRenderingPipeline, Supplier<ImmutableSet<Integer>> samplers, FogMode, boolean, boolean, boolean, boolean, CustomUniforms) throws IOException`
  - `public static FallbackShader createFallback(...)`
  - → 外部理论上可自行把一个 `ProgramSource` 编译成 `ExtendedShader`
- `net.irisshaders.iris.pipeline.transform.TransformPatcher#patchVanilla(name, vertex, geometry, tessControl, tessEval, fragment, AlphaTest, boolean, boolean, ShaderAttributeInputs, Object2ObjectMap)` —— `ShaderCreator.create` 内部就是把 `ProgramSource` 的源码交给它做 GLSL 版本/兼容性转换。**重要：这意味着我们拼进去的 GLSL 是"旧式方言"也能通过**（`texture2D`/`gl_FragData` 会被统一转换），不需要自己处理 `#version`。
- `net.irisshaders.iris.pipeline.IrisRenderingPipeline`
  - 字段：`CompositeRenderer beginRenderer/prepareRenderer/deferredRenderer/compositeRenderer`、`FinalPassRenderer finalPassRenderer`、`RenderTargets renderTargets`（private，无 getter）、`CustomUniforms customUniforms`、`Set<GlImage> customImages`
  - 方法：`getShaderMap()`、`getCustomUniforms()`、`shouldOverrideShaders()`、`setIsMainBound(boolean)`、`hasShadowRenderTargets()` 等
- `net.irisshaders.iris.pipeline.CompositeRenderer` —— `renderAll()`、内部类 `Pass`；`passes` 是 `ImmutableList`
- `net.irisshaders.iris.targets.RenderTargets`（要拿深度/挂 FBO 就必须碰它，但它是 private 字段）
  - `getDepthTexture()`、`getDepthTextureNoTranslucents()`、`getDepthTextureNoHand()`、`createGbufferFramebuffer(...)`、`createColorFramebuffer(...)`

### 8.2 三种注入粒度

**(a) 最省事：替换某个 pass 的源码（推荐做原型）**

切入点：`ProgramSet#getCompositeFinal()`（或 `getComposite()` 数组元素、`getGbuffers*()`）。

```java
// 伪代码：mixin 到 Oculus 的 ProgramSet#getCompositeFinal（@Inject RETURN, cancellable）
ProgramSource orig = (ProgramSource) ci.getReturnValue();
String frag = orig.getFragmentSource().orElseThrow();
String injected = frag.replace("/* DRAWBUFFERS:0 */", OUR_GLSL_FUNCTIONS + "\n/* DRAWBUFFERS:0 */");
// 用 private 构造器反射复制（保留 directives）
ProgramSource mine = newProgramSourcePreservingDirectives(orig, injected);
ci.setReturnValue(mine);   // 返回给 FinalPassRenderer 去编译
```

- 我们的 GLSL 就在 Iris 的 final pass 里逐像素执行，**读到的是 colortex3 的最终图像 + 全套包 uniform（含 `frameTime`/`framecounter`/自定义 uniform）**，写回 `gl_FragData[0]` → 屏幕。
- 这只是"叠在最后"，不参与 bloom/TAA/FXAA（因为 final 之后没有 pass 了）。
- 若想让图案参与泛光/TAA/FXAA：改 `getComposite()` 的元素（例如在 `composite4`(BLOOM) 之前插一层），或替换 `composite` 的源码让它写 colortex0/3。
- 若想让图案**参与光照**：替换 `gbuffers_*` 的片元源码（把图案写进 colortex0 反照率 + 相应 gaux），让它走完整的 deferred 光照。代价是必须自己补齐这个包期望的 gbuffer 数据（`gaux1/2/3` 的法线、材质掩码、自发光、平滑度…），否则光照结果会错（黑或过曝）。**这是"真正从头参与管线"的唯一方式，也是工作量最大、最容易和包版本耦合的方式。**

**(b) 追加一个新 pass**

`CompositeRenderer` 的 `passes` 是不可变列表，`FinalPassRenderer` 的 pass 集合也是构造期定死的。要追加：mixin `IrisRenderingPipeline` 构造器或 `CompositeRenderer` 构造器，用 `ShaderCreator.create(...)` 造 `ExtendedShader`，再构造一个 `CompositeRenderer$Pass` 塞进去（`Pass` 是内部类，要么反射，要么 mixin accessor）。**比 (a) 复杂得多，收益不大**（(a) 已经能在任意 pass 里跑我们的像素代码）。

**(c) 让 mod 自己的几何走 Iris 的 program**

即 §8.1 的 `ShaderCreator.create` → 得到 `ExtendedShader`（`instanceof ExtendedShader` 会让写掩码锁放行），再自己 `RenderType`/`VertexBuffer` 画。这条路能解决"世界渲染阶段看不见"，但 `create()` 需要 17 个参数（含 `GlFramebuffer`、sampler supplier、`IrisRenderingPipeline`），必须拿到 pipeline 内部状态 → 还是得 mixin/反射，且比 `AFTER_LEVEL` 方案复杂得多。**除非确实需要"我们的实体被包的光照照亮"，否则不值得。**

### 8.3 能否"只替换某个 gbuffer 程序的片元源码"

结构上可以 —— 见 §8.2(a)，`ProgramSet#getGbuffers*()` 是普通 getter，返回值可以被 mixin 换掉；`ProgramSource` 的内部字段都是 `final`，但**有 public 构造器可以重建**（或反射用 private 构造器保留 directives）。

涉及到的解析入口（回答"ShaderPack 怎么读源码、是否支持内存"）：

- `net.irisshaders.iris.shaderpack.ShaderPack(Path, ImmutableList<StringPair>)` —— 构造器要 `Path`（磁盘上的包根），字段 `sourceProvider` 是 `Function<AbsolutePackPath,String>`
- `net.irisshaders.iris.shaderpack.programs.ProgramSet` 构造器接受的是 **`Function<AbsolutePackPath,String>`**，即"任意来源的源码"；`ProgramSet#readProgramSource(...)` 只是调 `sourceProvider.apply(path)` 再 new `ProgramSource`
- **`#include` 的展开发生在包加载阶段**（`AbsolutePackPath.resolve("xxx")` + `sourceProvider.apply` 的递归），所以 `ProgramSource` 里的源码已经是"include 已展开、但尚未做 GLSL 版本转换"的状态；版本转换在绘制期 `ShaderCreator.create → TransformPatcher.patchVanilla` 做
- → **对 mod 而言：不需要"内存 ShaderPack"，只要拿到 `ProgramSet` 实例、把某个 getter 的返回值换成一个用内存字符串构造的 `ProgramSource` 即可。**

### 8.4 代价

| 项目 | 说明 |
|------|------|
| 版本绑定 | 极强。`ProgramSource` 构造器、`ProgramSet` getter 名、`ShaderCreator.create` 的 17 个参数、`TransformPatcher` 都是内部 API，Iris/Oculus 每次升级都可能变。Oculus 1.8.0 是 1.20.1 的**最后一个**版本（Iris 主线早已转向 1.21+），所以"绑定 1.8.0"在 1.20.1 上反而相对安全（不会再变）。 |
| 编译期依赖 | 要写 `@Mixin(targets="net.irisshaders.iris.shaderpack.programs.ProgramSet")` + 直接 new `ProgramSource`，就需要 **compileOnly oculus**。若想"Oculus 没装也能启动"，可以用 `targets = "..."` 字符串 + 内部全反射 + 一个 `IMixinConfigPlugin#shouldApplyMixin` 判断 Oculus 是否存在 → 可以不硬依赖，但代码量翻倍、且失去编译期检查。 |
| 代码量 | 最小原型（把图案拼进 final 的片元源码）≈ 1 个 mixin 类 + 1 个插件类 + 1 段 GLSL，约 150~250 行。 |
| 崩溃面 | 中高：mixin 目标是第三方 mod 的类，签名不匹配会在启动期直接崩；`ProgramSource` 的 `parent/directives` 传错会导致 draw buffer 数量不匹配 → 画黑/画花；在错误的线程/GL 上下文构造 program 会崩。必须包 try/catch 并回退到"不注入"。 |
| 是否需要 Oculus 依赖 | 必须（运行时）。编译期可选（反射方案）。 |
| 是否影响他人 | 只影响本客户端；纯客户端 mixin，不需要服务端同意；但会改变玩家任何一个光影包下的 final pass（应做开关 + 仅当 `IrisApi.isShaderPackInUse()` 时启用，并检测包名）。 |

### 8.5 一句话结论

> **"mod 主动把 GLSL 交给 Iris 执行"在 Complementary Reimagined + Oculus 1.8.0 上属于「只能内部注入」：官方 `IrisApi` v0 完全没有这个能力（9 个方法全是查询/开关/文字渲染），但 `ProgramSource` 有 public 构造器、`ProgramSet` 的源码来自 `Function`、`ShaderCreator.create` 是 public static，因此通过 mixin/反射把自定义 GLSL 塞进某个 pass 是结构上可行、且能真正参与光影管线的；代价是强版本绑定 + 必须依赖 Oculus 运行时 + 崩溃风险自负。**

## 9. 改光影包路线（问题 6）

### 9.1 最小改动面

方案一（推荐、最小）：**新增一个 `composite3`**（当前空号，位于 `composite2` 之后、`composite4`(BLOOM) 之前）。

```
shaders/world0/composite3.fsh    ← 我们的图案（#version 130 + include /program/xxx 或直接写）
shaders/world0/composite3.vsh    ← 拷贝 composite7.vsh 的内容（全屏 quad）
（如需下界/末地生效，同样在 world-1/、world1/ 各加一对）
```

- Iris 会按编号自动加载（`ProgramSet#readProgramArray`，上限 100，按存在与否收集）→ **不用改 `shaders.properties`**（除非要加 `program.world0/composite3.enabled=<条件>`）。
- 执行顺序：`composite2`(motion blur, 写 colortex0) → **`composite3`（我们，读 colortex0/colortex3 + depthtex，写 colortex3 或 colortex0）** → `composite4`(BLOOM，读 colortex3) → `composite5` → `composite6`(TAA) → `composite7`(FXAA) → `final`。
- 这样图案会被 **BLOOM / TAA / FXAA / 色调映射（final 里）全部处理**，视觉上就是"光影的一部分"。
- 需要"参与光照"（被方块挡住、被太阳照亮）则不能放这里，而要改 `gbuffers_*`（见 §8.3），工作量大幅上升 —— 但**在 composite 层用 `depthtex0` 做遮挡 + 用 colortex0 的颜色做环境光近似，通常已经够用**，这也是大多数"光影特效用 mod"的做法。

方案二（要参与 TAA/FXAA 但不想动编号）：把图案拼进 `shaders/program/composite7.glsl`（或 `composite6.glsl`）的 `gl_FragData[0] = ...` 之前。改动更小，但污染原文件、升级包时难合并。

### 9.2 分发上的现实问题（硬约束）

`License.txt`（包内）= **Complementary Agreement 1.3**：

- `1.2` 原样随整合包分发：允许（需署名 + 免责声明）。
- `1.3` 作为 **Modified Pack** 分发：允许，但必须同时满足：
  - a) 在 Modified Pack 的描述页显著署名原作者；
  - b) 原样保留 `License.txt`（一个字节都不许改）；
  - c) 名称里不能含 "Complementary"，且与原包名至少 3 个字符差异（加/删不可见字符不算）；
  - d) **"The Modified Pack must look noticeably different from The Pack in multiple common gameplay scenarios that must include daytime overworld visuals, regardless of the setting or variable changes."**

`1.3.d` 是真正的障碍：**"只加一个特效 pass、外观几乎不变"的改包，按字面就不满足 1.3.d，不能分发。** 也就是说：

- **自用**：随便改，零风险。
- **随 mod 分发**：不能只塞一个 composite 就发；要么把包改成"外观明显不同"的独立光影包（那就成了另一个作品），要么走 §8 的内部注入（不改包）。
- 另一个现实问题：用户手改 zip 很麻烦（要重新打包、要保持 `shaders/` 层级），而且一旦用户换光影包 / 更新包，我们的 pass 就没了 —— **改包路线本质上是"按包适配"，不是"mod 功能"**。

## 10. 最小验证实验（问题 7）

### 实验 A：`AFTER_LEVEL` + 自建 ShaderInstance —— 验证"写掩码锁"结论 + 拿到可用时机

| 项 | 定义 |
|----|------|
| 事件 | `net.minecraftforge.client.event.RenderLevelStageEvent`，`event.getStage() == RenderLevelStageEvent.Stage.AFTER_LEVEL`（Forge 47.3.22） |
| 前置 | `Minecraft.getInstance().getMainRenderTarget().bindWrite(true)`；`RenderSystem.enableDepthTest(); RenderSystem.depthFunc(515); RenderSystem.depthMask(false);`；`RenderSystem.disableCull()` |
| 几何 | 先画最简单的：屏幕空间全屏 quad（`Tesselator` + `DefaultVertexFormat.POSITION`，坐标直接用 NDC，配 `Matrix4f` 单位阵/正交阵），或直接把现有星刃几何用 `event.getPoseStack()` 画 |
| RenderType / Shader | 复用 `StarRenderTypes`（三角形/四边形 + 自定义 `ShaderInstance`），fragment 里用 `sin(...)`/`length(...)` 生成动态图案 |
| 预期 | 光影开、关都能看到图案；开关光影图案位置/形状一致；走到墙后图案被墙挡住（依赖 §5 的主 target 深度） |
| 失败判据 | ① 什么都没有：先查写掩码 —— 在绘制前读 `net.irisshaders.iris.gl.blending.DepthColorStorage.isDepthColorLocked()`（反射/调试打印），若为 `true` 说明时机仍在 world 渲染内（事件没派发到预期位置/被别的 mod 改了阶段）；② 有图案但完全不透明/黑：`ShaderInstance` 的 uniform 没写（`setShaderTexture`/`safeGetUniform`）或 blend 状态不对；③ 崩溃/黑屏：FBO 绑定或矩阵错（先去掉 `bindWrite`，改为在 `colorHolder` 上画，若此时可见就证明是"深度/FBO"问题而非"锁"问题） |
| 附带验证 | 在同一个实验里，把事件换成 `AFTER_ENTITIES` 再跑一遍：应当**完全看不见** —— 这一步就是写掩码锁的直接证据 |

### 实验 B：改包加 `composite3` —— 验证"参与泛化/后处理"

| 项 | 定义 |
|----|------|
| 改动 | `shaders/world0/composite3.fsh`（`#version 130`，`uniform sampler2D colortex3; uniform sampler2D depthtex0; uniform float frameTimeCounter;`）+ `composite3.vsh`（抄 `composite7.vsh`） |
| 内容 | `gl_FragData[0] = vec4(mix(baseColor, pattern, mask), 1.0);`，`/*DRAWBUFFERS:3*/`；用 `depthtex0` 做遮挡（`if (depth < 0.56) discard;` 之类），用 `frameTimeCounter` 做动画 |
| 预期 | 图案出现在 FXAA/BLOOM 之前 → 会被泛光和抗锯齿处理；被几何遮挡；`F3` 打开 Iris 调试（`shaderpack` 面板）后仍正常 |
| 失败判据 | ① 图案完全没出现：`composite3` 没有被加载（检查 `shaders.properties` 里是否有 `program.world0/composite3.enabled` 冲突；用 Iris 的 shader 调试开关看 pass 列表）；② 图案有但没被泛光/抗锯齿：编号插错位置（插到了 `final` 之后，即 `composite8`）；③ 整个画面变黑：`DRAWBUFFERS` 写错通道（必须写回 colortex3，不能写 colortex0 而最终 `final` 读 3） |

### 实验 C：内部注入（§8.2(a)）—— 验证"mod 提供 GLSL 给 Iris 执行"

| 项 | 定义 |
|----|------|
| 改动 | 1 个 mixin：`@Mixin(targets = "net.irisshaders.iris.shaderpack.programs.ProgramSet")`，`@Inject(method = "getCompositeFinal", at = @At("RETURN"), cancellable = true)`，把返回的 `ProgramSource` 换成"fragment 源码 = 原源码在 `/* DRAWBUFFERS:0 */` 之前拼接我们的函数 + `gl_FragData[0] = mix(orig, pattern, mask);`" |
| 依赖 | `compileOnly` oculus（或纯反射 + `MixinConfigPlugin` 条件加载） |
| 预期 | 不改包、不开实验 B 也能在任意光影包下看到图案；图案在 `final` 内执行 → 被 `IMAGE_SHARPENING` 影响，在 GUI 之下、手部之下 |
| 失败判据 | ① 启动崩溃：mixin 目标类/方法找不到（换 Iris 版本或 Oculus 未装）→ 必须做成"找不到就跳过"；② 图案出现但整个画面变暗/变白：拼接位置破坏了 `final.glsl` 的 `#ifdef`/变量作用域（拼在 `main()` 内最后一条 `gl_FragData` 之前，不要拼到文件末尾）；③ 只在自己屏幕有、别人没有：正常（纯客户端） |
| 额外验证 | 把注入点从 `getCompositeFinal` 换成 `getComposite` 的某个元素（例如 index 4 = composite5）→ 若图案开始被 TAA/FXAA 影响，就证明注入点选择正确 |

## 11. 未能确认 / 需实测的点

1. `MixinLevelRenderer#iris$beginLevelRender` 的 `@At(value="INVOKE", shift=AFTER)` 指向哪个具体方法，未逐字节确认（不影响本报告结论）。
2. Embeddium 0.3.31 加入后，Iris 的 chunk 渲染走 `SodiumTerrainPipeline`，gbuffer 绑定顺序可能与上面描述的"原版路径"略有差别；`AFTER_LEVEL` 的结论不受影响（它只看 `finalizeLevelRendering` 与主 target 深度）。
3. `TransformPatcher.patchVanilla` 对我们拼进去的任意 GLSL 的宽容度（例如在 `#version 130` 源码里插入含 `#if` 的片段）未实证 —— 实验 C 应先用极简代码（只加一个 `vec4` 混合）验证，再上复杂函数。
4. 手部渲染绑定的 FBO 细节未逐条确认；只确认它发生在 `AFTER_LEVEL` **之后**且先 `RenderSystem.clear(256)` 清深度。
5. 写掩码锁在 Embeddium 分块路径下是否对所有 mod 自建 RenderType 一律生效，建议用实验 A 的"AFTER_ENTITIES 对照"实测一次（预期：完全不可见）。
6. 本包 `composite3` 编号是否被 Iris 认为是"合法空号"——按 `readProgramArray` 的实现（按编号逐个尝试读文件）应当是合法的，但建议实验 B 直接验证（如果 `composite3` 不加载，就改用 `composite8`，它一定在 `final` 之前但 `composite7` 之后）。

## 12. 建议的落地顺序

1. **今天就能做**：星刃绘制切到 `RenderLevelStageEvent.Stage.AFTER_LEVEL`（+ `bindWrite(true)` + depth test），验证"光影下可见 + 被遮挡"。这一步预计改动 < 50 行，不动 Oculus。
2. **想更好看（自用）**：按 §9.1 在包里加 `composite3`，把函数图案写进光影包的后处理链；用 `depthtex0` 做遮挡。零 mod 代码。
3. **想随 mod 分发且要"真光影效果"**：按 §8.2(a) 做内部注入原型（先做实验 C 的最小版），确认三个版本（Oculus 1.8.0 + 本包 + Embeddium）稳定后再产品化；务必做开关、包名白名单、异常回退。
4. **不建议**：在 world 渲染阶段硬扛写掩码锁（路线 C）；依赖 `IrisApi` 做任何 program 级集成（能力不存在）；只改包就分发（License 1.3.d 过不去）。
